# Orden de implementación

## Decisión del propietario: monolito y aceptación local

La aplicación es un monolito de producto. `infra/compose.yml` es el único entorno interno de desarrollo, staging y aceptación; no se usa VPS, servidor remoto, host Linux dedicado, DNS público ni TLS wildcard real. Las capacidades que antes pedían staging, sandbox rootless, cuotas, S3, egress, gateway, observabilidad o rollback deben ejecutarse y validarse en Docker Compose con Docker Desktop y motor Linux. Silo es el S3 local. Preview y publicación usan `*.localhost`, con TLS local autofirmado si una prueba necesita HTTPS. El despliegue público final lo hará el propietario y no queda como issue pendiente.

Estado de Compose en `main`: Postgres, Redis, Silo, web, worker y el router Caddy local levantan con `npm run infra:up -- --web --worker --local-domains`; `npm run test:integration` valida Postgres/Redis/Silo locales. El controlador/sandbox aún no está integrado al Compose y faltan recorridos live de preview y la matriz de seguridad Docker, así que las issues que dependen de esos componentes siguen `PARCIAL` hasta que haya código y pruebas Compose verdes.

Plan creado a partir de [PROJECT_BRIEF.md](PROJECT_BRIEF.md). Leer [AGENTS.md](../AGENTS.md) antes de tomar una issue. Cada issue depende de la anterior; sus cuerpos en GitHub contienen tareas, archivos, variables, aceptación, pruebas y seguridad. El estado debe basarse en código y pruebas locales, no en despliegue público. `COMPLETA` exige checks aplicables y Docker local verdes; `PARCIAL` indica código faltante o pruebas/lint/typecheck/build fallidos.
