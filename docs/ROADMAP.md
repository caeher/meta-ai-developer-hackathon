# Orden de implementación

Estado local en `main`: la base del monorepo, servicios locales de Postgres/Redis/S3, persistencia multiusuario y tema Radix están implementados. El storage local usa Silo, fork compatible con MinIO, porque la distribución comunitaria de MinIO dejó de estar disponible. Las integraciones externas y capacidades futuras se declaran operativas solo tras su verificación.

Plan creado a partir de [PROJECT_BRIEF.md](PROJECT_BRIEF.md). Leer [AGENTS.md](../AGENTS.md) antes de tomar una issue. Cada issue depende de la anterior; sus cuerpos en GitHub contienen tareas, archivos, variables, aceptación, pruebas y seguridad. El estado actual está indicado en la fila de cada issue; no declarar capacidades posteriores disponibles sin implementarlas y verificarlas.

Estado de issue #4 actualizado el 2 de noviembre de 2026: la integración de Clerk, las rutas privadas, el contexto de owner y los fixtures de autorización ya están implementados. La issue sigue abierta hasta verificar sign-in, expiración y acceso cruzado con una instancia y dos usuarios Clerk de prueba; no hay credenciales de esa instancia configuradas en este entorno.

Estado de issue #5 actualizado el 2 de noviembre de 2026: tokens Tokyo Night, overrides de Radix, variables de Clerk, wrappers accesibles y galería local están implementados. La galería se revisó con Playwright Chromium en 390 y 1440 px; se guardaron capturas de la página y del diálogo en `docs/screenshots/`. El script `npm run screenshots:theme` comprueba contraste AA de tokens de texto, desbordamiento, foco de teclado, diálogo e hidratación. GitHub marca #5 como cerrada; la validación real de Clerk sigue pendiente en #4 y no bloquea el alcance visual.

Estado de issue #6: implementados CRUD paginado con ownership, transcript persistente e idempotente, dashboard, mensajes en texto plano y eliminación lógica con tarea durable de limpieza. La migración hace backfill ordenado de mensajes preexistentes. Los contratos e integración local son verificables con fixtures y PostgreSQL; la UI protegida requiere la instancia Clerk real, pendiente de la issue #4. No hay worker de limpieza, generación ni preview; quedan fuera de esta issue.

Estado local de issue #7 actualizado el 2 de noviembre de 2026: `/projects/[projectId]` usa el guard de sesión y la consulta con ownership ya implementados; presenta el editor responsive, permite renombrar, inserta opciones rápidas editables y guarda mensajes mediante el endpoint existente. Los contratos y vistas de plan/pasos/archivos/verificación están listos, sin datos de ejecución simulados. Preview, navegación, versiones, Publish y Share permanecen deshabilitados. `npm test` cubre las interacciones; `npm run test:integration` verifica la persistencia local. La issue #6 permanece abierta en GitHub aunque su alcance se describe implementado aquí; la autenticación real Clerk sigue pendiente en #4.

Estado de issue #8 (2 de noviembre de 2026): `npm run meta:smoke` pasó en Node 24.22.1 con una clave local de operador; `GET /models` mostró los IDs configurados para plan, código e imagen y `POST /responses` completó la respuesta sintética. No se guardaron la clave, headers, prompt completo ni el ID completo de respuesta. `npm test` valida errores offline con mocks; no se ejecutaron los opt-in facturables `--tools` ni `--image`. `docs/meta-api.md` registra los requisitos Contributor/ZDR, disponibilidad de cuenta/región y los costes vigentes revisados. La verificación real no conecta todavía Meta al editor.

Estado local de issue #9 (2 de noviembre de 2026): `MetaClient` valida el plan JSON, consume SSE incremental y ensambla/valida argumentos antes de emitir tool calls una sola vez cuando termina el response. La imagen se valida por base64, formato, tamaño y dimensiones. El replay usa `store: false` y razonamiento cifrado; no se muestran resúmenes privados. Los POST facturables no se reintentan por falta de clave idempotente documentada; los errores ambiguos deben reconciliarse con el run y ledger durable añadidos en #11 antes de que el orquestador posterior reintente. Fixtures offline cubren texto, llamadas paralelas y PNG sintético; no se ejecutó el smoke real ni una generación facturable. El chat aún no llama a Meta.

Estado local de issue #10 (2 de noviembre de 2026): el subconjunto upstream está fijado al commit `19d93f97c9c1ea0f8b306e77aa81e0d3e352d3e9`, con licencias, NOTICE y manifiesto SHA-256. `packages/skills` ofrece selección metadata-first, carga por tarea/referencia, presupuesto 8.000, fingerprint y registro de selección sin persistencia durable. Phaser 3.90 usa adaptaciones locales porque las skills Phaser upstream apuntan a 4.2. La entrega no conecta aún el editor ni Meta.

Estado local de issue #12 (2 de noviembre de 2026): `packages/sandbox` y `apps/sandbox-controller` implementan API privada con token, owner/proyecto resueltos en PostgreSQL, driver Docker rootless, UID interior unico, volumen local aislado con user quota dura, red por sandbox y reaper TTL. El controlador y `npm run sandbox:host-check` exigen Linux rootless, cgroups v2/systemd, Docker Engine 28 o superior, gateway de red `isolated` y `ENOSPC` en disco. `SANDBOX_DRIVER=disabled` por defecto; sigue pendiente aprovisionar y validar el host Linux dedicado con la imagen final y credenciales operativas.
Estado local de issue #13 (2 de noviembre de 2026): herramientas tipadas de archivos, npm exacto con --ignore-scripts, comandos limitados, limites de salida/timeout y servidor Vite interno con puerto 4173 registrado por lease. El helper openat rechaza traversal, symlinks y archivos especiales; el proxy permite unicamente rutas de registry aprobadas, pinning a IPv4 publica y redirects verificados. Los fixtures offline pasan; falta la ejecucion en host Linux dedicado, requerida para acreditar Docker rootless, DNS, SSRF, cuota y egress real. La feature continua apagada por defecto.

Estado local de issue #14 (2 de noviembre de 2026): emisión RS256 de grants de un uso, sesiones host-only particionadas, epochs de revocación en Redis, proxy HTTP/WebSocket y resolución del destino desde PostgreSQL están implementados con pruebas offline. El gateway también expone `GET /__session` para verificar cookies particionadas y acepta un formulario URL-encoded en el body para canje de primer nivel; rechaza grants en el query string. El acceso por DNS/TLS público, cookies del dominio real y validación en host Linux dedicado siguen pendientes; `PREVIEW_GATEWAY_ENABLED=false` por defecto.

Estado local de issue #15 (2 de noviembre de 2026): el editor solicita un grant al abrir/recargar, canjea la sesión, verifica la cookie desde el navegador y presenta estados de conexión, listo, error y expiración. El iframe usa `allow-scripts allow-same-origin` en el origen aislado de preview, sin navegación superior ni permisos delegados. Recarga y apertura de pestaña obtienen grants nuevos; la pestaña usa un formulario de primer nivel con `noopener` y no expone el grant en el URL. Atrás/adelante recorren únicamente rutas locales recibidas por `postMessage` validado por origen, fuente y schema. El selector muestra `Latest` y versiones del repositorio con ownership; restaurarlas espera al servicio de snapshots de #21. Unit tests, gateway integration y E2E de Chromium/Firefox/WebKit usan fixtures. Falta comprobar cookies/CSP con el dominio wildcard real y runtime del host Linux dedicado; la feature permanece apagada por defecto.

Estado local de issue #11 (2 de noviembre de 2026): apps/worker publica el outbox de Postgres a BullMQ/Redis con IDs estables y generaciones. Enqueue/cancel verifican Clerk y owner; reservas por usuario serializan en Postgres, y el ledger registra consumo medido. Los locks usan heartbeat, lease y fencing; el reconciliador reencola runs con lease vencido y rechaza resultados de workers antiguos. RUNS_ENABLED=false por defecto. La integracion cubre Postgres y Redis reales, limites concurrentes, cancelacion y kill/restart del worker.

Estado local de issue #16 (2 de noviembre de 2026): el worker vincula cada run a un mensaje de usuario guardado y exige confirmación de términos Contributor/18+. `MetaClient` genera un plan estricto con objetivo, pasos, archivos y verificaciones; el plan y sus eventos se guardan antes de crear o modificar el sandbox. El router de skills registra hashes por run; el orquestador ejecuta solo herramientas Zod permitidas, una por vez, conserva resultados por `call_id`, revalida lease/owner antes de escribir eventos y cobra los tokens reportados por Meta. Tests/build de npm se ejecutan automáticamente cuando existen; se permite un intento de reparación. `RUNS_ENABLED=false` sigue siendo el valor por defecto. Meta real, consentimiento visual en el chat (#17), host Linux rootless y recuperación de una respuesta Meta ambigua tras crash requieren verificación externa o la issue posterior; no se afirma que el juego esté completo.

Estado local de issue #17 (2 de noviembre de 2026): el chat guarda el mensaje, exige consentimiento Contributor/18+ y encola runs con clave idempotente. La ruta SSE proyecta eventos privados a un contrato versionado, soporta Last-Event-ID, replay, heartbeat, backpressure y cancelación. El editor recupera progreso tras recarga y solo renueva preview con el evento de health check. RUNS_ENABLED=false; faltan la verificación con Clerk real, Meta habilitado, dominio/TLS y host Linux dedicado.

Estado local de issue #18 (2 de noviembre de 2026): la plantilla Phaser tiene lockfile, build estático sin sourcemaps, assets locales inventariados, audio procedural, controles accesibles, cuatro géneros, estado observable de solo lectura en desarrollo y suites de lógica/navegador. El worker materializa la plantilla en workspaces vacíos, instala dependencias exactas sin lifecycle scripts, ejecuta test/build y arranca Vite tras health check; un marcador durable permite reanudar y evita sobrescribir proyectos personalizados. Los tests locales no acreditan Docker rootless, egress de npm ni HMR a través del gateway real. Falta validarlo en el host Linux dedicado con Docker Engine 28+, gateway y dominio/TLS; la generación sigue apagada por defecto.

Estado local de issue #19 (2 de noviembre de 2026): `generate_image` está conectado al worker con reserva de cuota, registro durable/ambigüedad, validación y normalización de formatos, alpha y frames, hoja de contacto y heurística 3×3.
